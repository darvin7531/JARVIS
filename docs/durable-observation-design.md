# Durable read–inference–verification design (not implemented)

This is a proposed design, not a security guarantee or a description of current behavior. The existing read-only agent proposes a read before the broker reads, and verifies against an owner-supplied expected value. It does not pass an unknown observation back to inference.

## Scope and trust

A trusted owner supplies the task revision, exact resource and classification, expiry, budgets, inference configuration, and two distinct exact one-shot read approvals. The model and read value are untrusted data, never authority. The only supported tool is the existing mock read; no writes, shell, or new tool selection. Storage and the owner process are trusted and not a sandbox. Persisted observations are plaintext like existing mock state; do not use secrets. The configured inference route must independently admit the observation's classification; a loopback address alone is not a privacy guarantee.

The model returns a bounded structured claim containing an exact observed value, not an arbitrary success verdict. Deterministic verification compares that claim, the first observation, and a separately approved second broker read, requiring the same exact resource and class. A missing resource must not be confused with an empty value: add an explicit presence bit at the mock read boundary before using this design. A mismatch means verification failed, not an automatic retry. This verifies a value at two instants, not that it never changed in between or will remain unchanged afterward. Only verified data can be reported as verified; escape all output and treat model text as hostile.

## Durable state machine

Add a versioned, schema-validated continuation row keyed by task and revision with immutable owner configuration binding, a phase, and a unique generation/claim token. Bound every stored observation, model response, and context in bytes before persistence or dispatch. Enforce one live continuation per revision. Every transition is a SQLite immediate transaction with a compare-and-swap on phase and generation; commit phase, counters, bounded payload and audit event together. Never accept a caller-provided continuation payload or allow a new owner file to alter the persisted binding. An owner configuration digest must use an unambiguous canonical encoding and cover all authority-bearing fields, including expiry, budgets, provider policy and approval identifiers.

1. Atomically claim `read_pending` before dispatching the first approved broker read. The broker must atomically consume the exact approval, charge its tool budget and persist the intent as it already does. On success, atomically persist the bounded observation and advance to `observed`; only the holder of the generation token may finish. A crash after the broker records its outcome but before observation persistence leaves `read_pending`: the result is unavailable and requires owner reconciliation, not another read.
2. Atomically reserve an agent step and advance `observed` to `inference_pending` before provider dispatch. Construct the prompt from the immutable trusted context plus a clearly delimited, length-bounded untrusted observation; prompt text does not override the output schema or policy. Apply existing shared inference admission and settlement. Persist the strictly parsed claim and advance to `claim_ready` only after terminal status and usage are validated. Malformed, incomplete, over-limit, timed-out, cancelled, or unsettled inference fails closed. In particular, never redispatch a pending request after a crash.
3. Atomically claim `verify_pending` before the independent second approved read. Compare its returned presence, classification and bytes against both the persisted observation and the claim; atomically persist `verified` or `verification_failed` with its audit event. Crash or storage failure between dispatch and durable result leaves `verify_pending`, not success, and requires reconciliation.

The transaction holding the phase claim must not remain open over a provider or broker call. A second process cannot steal a live claim merely because time passed: leases without fencing cannot stop the original process from later dispatching. On any pending phase, recovery must stop all clients, preserve evidence, inspect tool intents and inference reservations, and use the existing trusted reconciliation procedures. Closure is terminal; create a new task revision and fresh approvals for another attempt. No budget refund, approval restoration, automatic replay, or exactly-once claim. The old-backup rollback problem remains unsolved without an external trusted monotonic anchor.

Check cancellation and expiry before each admission and dispatch, and after blocking operations. Cancellation cannot retract already sent bytes or undo a consumed approval. If cancellation occurs after dispatch, preserve pending/uncertain state and charges; never publish verified success solely from a cancellation response. An atomic claim alone does not fence stale in-process dispatch: the implementation must either prohibit automatic takeover entirely as above or introduce a fencing mechanism honored at every side-effect boundary. Preserve existing task-revision checks, restore quarantine, and globally pending tool-execution blocks.

## Required CI evidence before enabling

- A nonempty unknown value reaches the actual configured inference boundary; a correct structured claim and separately approved second broker read verify it. Wrong claim, changed state, absent versus empty, wrong class/resource, malformed/oversized output and untrusted instructions fail safely.
- Two concurrent processes race at each claim; exactly one dispatches. Synchronize and kill subprocesses at read intent, post-read/pre-persist, inference dispatch, and second-read/post-execution boundaries. Reopen storage and assert phase, pending intents, approvals, budgets and absence of replay or false success.
- Exercise cancellation and expiry on both sides of each dispatch, shared token and tool budgets, unresolved settlement, stale revisions, changed owner configuration, restored snapshots, storage failures and independently seeded persisted state.
- Run the product's existing CI, including a configured-provider integration without secrets. A mock-only result cannot establish real-provider behavior. No local builds or tests are authorized for this work.
