# JARVIS foundation

Linux, Rust 1.89.0. No credentials or LLM needed. Run `cargo run --locked`; press Enter, send SIGINT or SIGTERM to stop. EOF alone does not stop the service; stdin errors are ignored, so service managers may use `/dev/null`.

Optional `--config path.json` accepts an empty JSON object (`{}`); there are currently no configuration options. Config files are limited to 64 KiB; unknown fields, malformed JSON, oversized and unreadable files are rejected without echoing input or paths. Do not put secrets in config.

Development checks (also run in CI):

```sh
cargo build --locked
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Service logs are JSON lifecycle events or a fixed error code. Observed lifecycle output errors cause failure at shutdown. To keep shutdown bounded when stdout is blocked, the service waits 100 ms for the output worker; on timeout it exits successfully and pending lifecycle events may be lost, with later output errors unobserved. Chat has a separate local inference interface described below; there is no task engine or secret manager.

Storage workspaces are private directories (no group or other permissions); opening an existing workspace with broader permissions fails without changing them. The database must be a regular file, not a symlink. Schema objects and SQLite integrity and foreign keys are checked before migration. These checks assume the workspace is not concurrently modified by untrusted processes; they do not protect against another process with the same user privileges or pre-existing hard links and ACLs.

Backups retry SQLite steps for approximately three seconds with 100 ms SQLite busy timeouts; this is not a hard wall-clock deadline: individual SQLite calls, filesystem I/O, scheduling, and publication can take longer. A backup is published only after completion and never replaces an existing destination. The destination parent must be owned by the effective user and not group- or world-writable; all path ancestors, ACLs, and same-user processes must also be trusted against substitution. If the final parent-directory sync fails, backup returns an error but the destination may already exist; inspect it before retrying. New evidence provenance and classification must be nonblank strings of at most 1024 bytes; they are not authenticated security labels. Observed time, when present, must be a valid UTC timestamp in `YYYY-MM-DDTHH:MM:SSZ` or `YYYY-MM-DDTHH:MM:SS.sssZ` format. Existing legacy metadata is not retroactively validated.

Configured chat connects to a loopback Ollama-compatible server and requires `curl` on PATH. Example `chat.json` (no secrets):

```json
{"models":[{"name":"smollm2:135m-instruct-q4_0","tier":"t1","capabilities":["text"],"allowed_data":["public"],"trusted_no_truncation":true,"port":11434}],"budget":{"workspace":"/path/to/existing/private-workspace","limit_tokens":100000,"max_input_tokens":2048}}
```

Loopback is not a privacy guarantee: Ollama can forward requests to cloud models, and a local server can be malicious. By default, only public data can be sent, even if `allowed_data` lists other classes. To permit internal or sensitive data, the operator must explicitly set `"trusted_local":true` on each model profile, after verifying and controlling the server and its model, disabling cloud features (e.g. start Ollama with `OLLAMA_NO_CLOUD=1`), and applying appropriate network isolation. This flag is an operator assertion, not attestation; JARVIS cannot verify that the server or model is private. The real transport is private to the CLI; it applies this policy before invoking it.

Sensitive prompts must use `--data sensitive --stdin` as the final option, with UTF-8 prompt bytes supplied on stdin until EOF (maximum 1 MiB); argv prompts marked sensitive are rejected, but rejection cannot erase argv exposure that already occurred. Avoid shell history or process arguments when supplying sensitive text; protect the pipe and output too. `--stdin` also works for other data classes. Sensitive terminal stdin is rejected to prevent echo; supply input via a protected pipe or file. Stdin reading is subject to the request timeout and SIGINT/SIGTERM; close it to start inference. For example, `jarvis chat --config chat.json --data sensitive --stdin < private-prompt.txt`. Pipe stdin and stdout use independently reopened nonblocking descriptors on Linux (/proc must be mounted); socket stdin and stdout are rejected. Regular files and devices may still block in the kernel, so their deadlines are not guaranteed.

Run `jarvis chat --config chat.json ping` for the only built-in T0 rule: exact `ping` prints `pong` without a model or tool execution; `--tier t0` also selects this rule. Other T0 prompts and `--model` with T0 are rejected; no general-purpose procedure runtime is provided.

Run `jarvis chat --config chat.json --tier t1 --data public 'Hello'`. Optional `--model NAME` selects a configured model, `--tier` accepts `t1` through `t3`, `--require` accepts `text`, `vision`, or `tools`, and `--data` accepts `public`, `internal`, or `sensitive`. Configuration labels are operator assertions, not verified model capabilities or security guarantees; this interface sends only text and grants no tool execution. Output streams to stdout; token usage is JSON on stderr. Requests default to 128 output tokens, 64 KiB output and 120 seconds; set `"limits":{"max_tokens":128,"max_output_bytes":65536,"timeout_seconds":120}` in the JSON to change them. Without `--tier`, exact `ping` selects T0; `complex:` or case-insensitive words beginning with `architecture`, `incident`, `critical`, `архитектур`, `инцидент`, or `критическ` select T3; otherwise `code:` selects T2 and all other prompts select T1. These lexical hints can miss complex tasks or match irrelevant text; use an explicit tier when classification matters. Explicit `--tier` overrides classification and `--model` selects a named profile across tiers, still subject to data and capability filters. This CLI accepts text only: `--require vision` and `--require tools` are rejected even when a model profile claims them. SIGINT/SIGTERM cancel active generation. On failure after generation begins, stderr reports `{"usage":null}` when final usage is unavailable, followed by an error; a token-length termination instead reports available usage and `budget_exceeded`; partial stdout must not be treated as a completed response. No provider fallback occurs. Each CLI invocation issues one request; a shared cross-process concurrency limit is not implemented. `--openai` remains a nonfunctional experimental placeholder.

The supported backend is an Ollama-compatible loopback server; there is no paid backend or monetary budget enforcement. The output byte limit is enforced during streaming; the token limit is requested from Ollama and checked against its final reported usage, not independently counted during streaming. Prompts are limited to 1 MiB and config files to 64 KiB. The private transport requires callbacks to return promptly.

Configured real chat requires a shared token budget, for example `"budget":{"workspace":"/path/to/existing/private-workspace","limit_tokens":100000,"max_input_tokens":2048}`. Create the workspace with the storage API first. The limit is cumulative input plus output tokens, not money; the first reservation establishes a persistent workspace limit and mismatched limits fail closed. Existing version-5 workspaces with budget entries have no verifiable limit and fail closed; use a new workspace only after deliberate owner reconciliation. Before contacting the server, JARVIS atomically reserves `max_input_tokens + limits.max_tokens`, then replaces that reservation with validated terminal usage. Missing usage, cancellation, crashes, transport failures and failed settlement leave an unresolved reservation that blocks further requests; there is no automatic refund or reconciliation. Backups include reservations and a pending restore marker (budget row id -1), so budget admission is blocked until an operator reconciles it. Older backups created before this safeguard do not contain the marker and must not be used without manual reconciliation. All cooperating processes must use the same operator-controlled workspace; separate workspaces, modified binaries, direct server access, or untrusted configuration are outside this boundary. Synthetic mock and T0 paths do not contact a server and are exempt.

The input bound is requested as Ollama `num_ctx`; the output bound is requested as `num_predict`. These are requests to the server, not independently proven hard token bounds. Model templates, context handling, server behavior or dishonest usage reports can violate the bound, so this is not a hard guarantee against overspending. JARVIS sends `truncate: false` and `shift: false` to reject oversized prompts and prevent context shifting, but older or incompatible servers can ignore them. Each selected model requires `"trusted_no_truncation":true`: this is an explicit operator assertion that the server is a tested compatible runtime and remains under operator control, not server attestation. The supported, tested server is Ollama 0.13.5, the exact image digest pinned in `.github/workflows/ollama.yml`; operators must independently deploy and trust that runtime. JARVIS cannot verify server identity or the assertion; an older, substituted, or dishonest server can still silently truncate. If reported input or output exceeds its requested bound, terminal output is rejected and validated actual usage is still charged; subsequent reservations fail when usage exceeds the limit. An output-byte limit violation in a terminal frame also charges validated usage; for a nonterminal frame the stream is stopped immediately and the reservation remains charged because usage is unknown. That reservation can undercount actual usage. The pre-request reservation is not a hard cap because the server may exceed it. No amount of accounting can retroactively prevent server-side work that exceeds the reservation.

Shared budget requests are serialized per workspace: any unresolved reservation blocks all subsequent budgeted requests, including after restart. This is necessary because requested token bounds are not enforceable. Version-6 and older budget entries are preserved and conservatively treated as unresolved on migration, even if previously settled; stop old JARVIS processes before upgrading, since older versions do not honor this guard.

For recovery, stop all clients and the model server, back up the workspace, and reconcile each pending row against trustworthy usage records. If exact usage is unavailable, choose an operator-determined conservative charge (at least the existing reservation and any known usage); no finite charge can guarantee coverage of unknown server work. With exclusive access, use a SQLite transaction to update each `inference_budget` row: set `tokens` to the reconciled charge and `pending` to 0 together. Never clear or reduce a pending charge based on untrusted reports, elapsed time, or process disappearance. Verify all charges and the persistent limit before restarting; if uncertainty cannot be accepted, keep the workspace blocked. For a restored backup, row -1 is the restore marker: reconcile all usage omitted since the snapshot, add a conservative charge to that row without reducing its existing tokens, and only then clear its pending flag. Reconcile every other pending row independently; do not clear them in bulk. If trustworthy records cannot establish omitted usage, leave the marker pending unless the operator explicitly accepts an unbounded risk. For a migrated version-5 ledger whose persistent limit is NULL, set it to the independently verified original limit in the same exclusive maintenance transaction only after reconciling its charges; otherwise it remains blocked. These safeguards cannot detect a database copied outside the backup API or a pre-safeguard backup, and cannot prove that unknown later usage was accounted for. A copied or rolled-back unmarked database may admit requests immediately; the operator must quarantine it before opening it for budgeted use, independently reconcile all omitted usage and pending reservations against trustworthy records, and verify the original limit. Without trustworthy external state, JARVIS cannot distinguish such a rollback from a current workspace or recover the missing usage. If usage is unknown, keep it offline unless the operator explicitly accepts unbounded risk; a conservative estimate cannot guarantee coverage.
